# Remediation Baseline

## 1. Current Architecture
The application is built on a React 18 single-page application (SPA) architecture, served via Vite during development and a Node.js (Express v4) server in production. It uses Tailwind CSS for styling and Recharts for data visualization. The backend integrates with Firebase Authentication for identity management and Cloud Firestore for NoSQL data persistence. The `@google/genai` SDK is used server-side for AI integrations, specifically with Gemini 3 models (gemini-3.1-pro-preview, gemini-3.5-flash, gemini-3.1-flash-lite). The architecture incorporates several sub-modules for safety, evidence grounding, wearable data processing, and professional dashboard access.

## 2. Current Data Flows
- **User Authentication:** Clients authenticate directly with Firebase Auth. The resulting JWT is sent as a Bearer token to the Express backend (`/api/*` routes) where it is verified using the Firebase Admin SDK.
- **Application State (Firestore):** Users write mood logs and assessment data directly to Firestore from the client, governed by Firestore Security Rules.
- **AI Interactions:** Client sends chat messages to the Express backend. The backend uses the Gemini API to process the prompt (along with any grounded evidence or search tool context) and returns the generated response.
- **Wearable Data (Simulated):** A simulated device (`SimulatedDevice.ts`) generates mock physiological data on the client side, pushing it through a processing pipeline (`DataPipeline.ts`) and aggregating it in a local memory store. It does not currently persist this raw data to a secure database.
- **Professional Dashboard (Simulated):** Client requests patient data via an `AccessManager` that utilizes a mock data store (`MockDataStore`). Professional and patient identities are currently hardcoded, and consent is automatically granted on component mount.

## 3. Trust Boundaries
- **Client to Firebase (Auth & Firestore):** Trusted via Firebase SDKs and JWTs. Security relies on proper implementation of Firestore Rules.
- **Client to Express Backend:** Protected by the `requireAuth` middleware (JWT validation) and `helmet`/`rateLimit` for basic API security.
- **Express Backend to Gemini API:** Trusted server-to-server connection authenticated via a secret `GEMINI_API_KEY`.
- **Professional Dashboard:** Currently lacks a secure trust boundary; it operates with simulated, hardcoded identities and auto-granted consent that bypasses real authorization checks.

## 4. Sensitive-Data Flows
- **Self-Reported Moods & Assessments:** Stored in Firestore, tied to `uid`.
- **Raw Sensor Data (Simulated):** Highly sensitive physiological data (PPG, EDA, Temperature) is generated client-side but not securely persisted or transmitted.
- **AI Chat Logs (History):** Chat history is sent to the backend for context but relies on the client for state management in the current implementation.
- **Safety Events:** Generated by the `safetyEngine.ts` when critical risks are identified. Currently relies on deterministic keyword matching and does not persist events securely.
- **Professional Access:** Aims to handle PHI (Protected Health Information), but currently operates on a mock data store with simulated consent.

## 5. Known Weaknesses
- **Simulated Physiological Calculations:** `SimulatedDevice.ts` generates basic noise or sine waves instead of actual medical algorithms. Do NOT claim that these simulated measurements are real.
- **Fake Data Deletion:** The `/api/user/data` endpoint simulates secure data deletion by returning a success message without actually removing data from Firestore or clearing logs.
- **Automatic Professional Consent:** `ProfessionalDashboard.tsx` automatically grants consent on component mount, bypassing real authorization workflows.
- **Hard-coded Professional/Patient Identities:** `ProfessionalDashboard.tsx` uses hardcoded `professionalId` and `patientId` (e.g., in `App.tsx`).
- **Safety-Engine Weaknesses:** `safetyEngine.ts` is mostly deterministic keyword matching and lacks robust LLM classification integration; it is a PARTIAL/SIMULATED implementation.
- **Evidence Persistence Weaknesses:** `evidenceStore.ts` uses an in-memory vector store that loses all embeddings and data upon container restart.
- **Privacy Weaknesses:** Data lifecycle policies (e.g., retention periods) defined in `PrivacyLifecycle.ts` are not actively enforced by scheduled jobs or TTL indexes in Firestore.
- **Security Weaknesses:** Rate limiters and basic HTTP headers are present, but the application lacks robust validation against complex injection attacks beyond basic Zod schemas.
- **Incomplete Firebase Authorization:** `firestore.rules` lacks rules for professional access, safety events, sensor insights, and other planned data collections.
- **Sensitive Telemetry Concerns:** Logging practices (e.g., in `AuditLogger.ts`) may inadvertently expose sensitive data if not strictly sanitized before being sent to external monitoring services.
- **Production Configuration Problems:** Environment variables (`.env.example`) and deployment configurations need validation to ensure secrets aren't leaked and production optimizations are applied.
- **Incomplete Tests:** While tests exist (`npm run test`), they cover the simulated and partial implementations, giving a false sense of security for production-readiness.

## 6. Implementation Categorizations
- **Firebase Authentication:** REAL
- **Firestore Rules:** PARTIAL (missing rules for advanced features)
- **Express API:** REAL
- **AI Assistant:** REAL (using Gemini API)
- **Automated Tests:** PARTIAL (testing simulated/mocked logic)
- **`src/lib/wearables/SimulatedDevice.ts`:** SIMULATED
- **`src/components/professional/ProfessionalDashboard.tsx`:** SIMULATED (consent and mock data)
- **`src/lib/professional/AccessManager.ts`:** SIMULATED (MockDataStore)
- **Data Deletion (`server.ts`):** SIMULATED
- **`src/lib/safetyEngine.ts`:** PARTIAL/SIMULATED (primarily deterministic)
- **`src/lib/evidenceStore.ts`:** PARTIAL/SIMULATED (in-memory)
- **`src/lib/wearables/processing/*`:** SIMULATED logic

## 7. Proposed Remediation Order
1.  **Authentication & Authorization Core:** Implement REAL data deletion in `server.ts` and replace hardcoded identities/automatic consent in `ProfessionalDashboard.tsx` with robust Firestore-backed authorization.
2.  **Firestore Rules Expansion:** Update `firestore.rules` to cover all data collections (professional access, safety events, insights) to secure the backend.
3.  **Data Persistence Upgrades:** Migrate `evidenceStore.ts` from in-memory to a persistent vector database (e.g., pgvector or Pinecone) and implement TTL/scheduled jobs for `PrivacyLifecycle.ts` retention policies.
4.  **Safety Engine Enhancement:** Upgrade `safetyEngine.ts` to utilize synchronous, lightweight LLM classification (e.g., Gemini Flash) for nuanced risk detection instead of relying solely on keywords.
5.  **Wearable Integration Preparation:** Refactor wearable processing pipelines to handle real WebBluetoothDevice data streams, preparing to replace `SimulatedDevice.ts`.
6.  **Telemetry & Audit Hardening:** Review and sanitize all logging mechanisms to ensure PHI is never leaked to external monitoring services.

## 8. Explicit List of Components That Must NOT Be Changed Unnecessarily
- Existing React + TypeScript + Vite + Express + Firebase + Gemini architecture.
- Core Firebase Authentication flow (`AuthContext.tsx`, `firebase.ts`, `firebase-admin.ts`).
- Existing Express API structure (`server.ts`) and middleware (`auth.ts`).
- The functional AI assistant interface and Gemini integration logic (`Assistant.tsx`, `/api/chat` route).
- Existing Recharts implementations and Tailwind CSS styling patterns.
- Existing tests (`src/tests/*`) — they should be updated alongside remediations, not deleted.
